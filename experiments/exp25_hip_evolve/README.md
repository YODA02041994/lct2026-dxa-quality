# Эксп. 25 — эволюция признаков укладки бедра (DeepSeek как оператор мутации)

Повод: в спецтреке ФСП эволюция формулы подбора дала +0,13 nDCG на нетронутых мирах. Проверяли, переносится ли приём на DXA.

Схема (как в ShinkaEvolve/OpenEvolve): модель пишет функцию `extra(lm, img, side, h, w)` — до четырёх геометрических признаков по
ориентирам локализатора вне обучения и снимку; фитнес — программа (`fitness.py`): OOF ROC-AUC логистической регрессии боевых признаков
(наклон диафиза, ансамбль сетей) плюс признаки кандидата, GroupKFold(3) по исследованиям на **поисковой части (60 % исследований:
91 снимок, 22 нарушения)**. Код кандидата проверяется по запрещённым конструкциям и исполняется в отдельном процессе с урезанными builtins.
Три лучших кандидата один раз проверяются на **отложенной части (40 %: 59 снимков, 14 нарушений)**. В бой — только при ΔAUC ≥ 0,03 и
нижней границе 95 % ДИ (парный бутстреп по исследованиям) > 0.

Запуск: `PYTHONPATH=src python experiments/exp25_hip_evolve/prepare.py`, затем `python experiments/exp25_hip_evolve/evolve.py --generations 8 --children 4`.
Ключ DeepSeek читается по ssh в переменную процесса (`llm_client.py`), в файлы и вывод не попадает.

Результат 17.10.2026: 32 обращения, $0,023.

**Ворота не пройдены, в модель ничего не вошло.** Прирост на поиске (+0,05…+0,07) — подгонка под 22 нарушения: на отложенных
исследованиях те же признаки ухудшают ранжирование. Это согласуется с эксп. 18 (отбор признаков на малых данных не обобщается) и с тем,
что ансамбль сетей по вырезкам вертела уже несёт ту же информацию. Вывод для доклада: автоматический поиск признаков проверен и
отклонён по заранее заданным воротам, а не по желаемому результату.
