## Масштаб (ответ организатора 16.09 vs то, что в файлах)

Организатор: пиксель сканера **0,6 мм по X, 1,05 мм по Y**, один вариант аппарата во всех наборах.

Но в выгруженных 8-битных картинках это не сходится напрямую:

| Источник | мм/px по X | мм/px по Y |
|---|---|---|
| Ответ организатора (нативный скан Lunar Prodigy) | 0,60 | 1,05 |
| `ExposedArea` 180 × 193 мм при 300 × 289 px (типичный файл) | 0,60 | ≈ 0,67 |
| Визуально | картинки выглядят анатомически пропорциональными, т.е. ≈ изотропными |

### Проверено 16.09 — выгрузка изотропная, ≈ 0,6 мм/px

| Тест | Результат |
|---|---|
| `ExposedArea` по всем файлам, позвоночник (300 px, n = 99) | `a0/cols` = **0,600** мм/px; `a1/rows` медиана **0,607** |
| `ExposedArea`, бедро (280 px, n = 138) | `a0/cols` = **0,643**; `a1/rows` медиана **0,660** |
| `ExposedArea`, 248 px (№70, эндопротез) | 0,605 / 0,608 |
| Шаг позвонков (тело + диск) по автокорреляции профиля яркости, 46 снимков | медиана **53 px** → при анатомическом шаге L1–L4 33–37 мм Y = **0,62–0,70** мм/px. При 1,05 мм/px шаг был бы ≈ 33 px — не наблюдается |
| Головка бедра на сетке (`Для теста/CR000000_ППОБ`) | ≈ 65 × 65 px — **круг**. При 0,6 × 1,05 была бы 65 × 37 |
| Тело позвонка на сетке (`CR000000_ПОП`) | ширина ≈ 60 px, высота ≈ 35–40 px → W/H ≈ 1,5–1,7 = анатомическая пропорция. При анизотропии было бы ≈ 2,9 |

**Вывод.** 1,05 мм по Y — нативный шаг строк сканера; экспорт в DICOM CR пересэмплирован в квадратный пиксель.
Рабочие константы (`dxaqc.labels`): позвоночник **0,60 мм/px**, бедро **0,65 мм/px** (по обеим осям), погрешность ≈ ±10 %.
Для критерия поля ROI: 3 см ≈ 46–50 px, 2 см ≈ 31–33 px. Пороги всё равно калибруем на разметке, константы — для перевода в сантиметры в отчёте.

## Манифест изображений (20.09) — `data/work/manifest.csv`

Собирается `PYTHONPATH=src python scripts/make_manifest.py`; в git не хранится (производное от данных организатора).

| Что | Как определяется | Проверка |
|---|---|---|
| Область | ширина кадра: 300 px — позвоночник; 280 px — бедро; **248 px — бедро в ортопедическом режиме** (эндопротез, кадр ~248×403, исследование №70) | 252 снимка, без области — 0 |
| Сторона бедра | положение костной массы таза в верхней половине кадра (таз справа → правое бедро); в паре стороны принудительно разные | 73 пары из 73 разошлись по сторонам; 5 одиночных из 5 совпали с разметкой; 5 слабых случаев (№6, 8, 47, 89, 96) проверены глазами |
| Истина | колонки критериев, не «Итог» | размечено 249 (99 + 72 R + 78 L), не размечены 3 бедра с эндопротезом (№66 R, №70 R и L) |

Итог по классам (уровень снимка): с нарушением **72 из 249**; укладка позвоночника 6, ось 10, артефакты 17;
укладка бедра 36, поле ROI 7. Признак «положение диафиза» для стороны отброшен: ошибался в 9 парах из 73.

## Что из этого следует для решения

1. Хранить два идентификатора: имя папки (ключ разметки) и StudyInstanceUID (требование ТЗ).
2. Дедуп по хэшу пикселей; строка в выходе — на каждый файл, предсказание общее для дубликатов.
3. Область и сторону определять по изображению; суффикс имени файла — только подсказка.
4. Масштаба в мм нет → критерий поля ROI реализуем в относительных единицах, пока эксперты не дадут мм/px.
5. Кросс-валидация строго по исследованиям (GroupKFold), бутстрэп-ДИ; при 3–10 положительных честно писать широкие интервалы.
6. Аугментации: без поворотов (убьёт критерий оси), без горизонтальных отражений (убьёт сторону бедра) — или отражать с одновременной сменой метки стороны.
7. Спорные случаи (сколиоз, перелом, эндопротез) вынести в отдельный список и решать по ответу экспертов.
