## Масштаб (ответ организатора 16.09 vs то, что в файлах)

Организатор: пиксель сканера **0,6 мм по X, 1,05 мм по Y**, один вариант аппарата во всех наборах.

Но в выгруженных 8-битных картинках это не сходится напрямую:

| Источник | мм/px по X | мм/px по Y |
|---|---|---|
| Ответ организатора (нативный скан Lunar Prodigy) | 0,60 | 1,05 |
| `ExposedArea` 180 × 193 мм при 300 × 289 px (типичный файл) | 0,60 | ≈ 0,67 |
| Визуально | картинки выглядят анатомически пропорциональными, т.е. ≈ изотропными |

Вероятно, экспорт в DICOM CR пересэмплирован. Прежде чем считать «3 см / 2 см», нужно **сверить масштаб по
анатомии** (диаметр головки бедра ≈ 45–50 мм у взрослых, высота тела L3 ≈ 25–30 мм) на 10–20 картинках
и зафиксировать рабочий мм/px в коде. Задача #15.

## Что из этого следует для решения

1. Хранить два идентификатора: имя папки (ключ разметки) и StudyInstanceUID (требование ТЗ).
2. Дедуп по хэшу пикселей; строка в выходе — на каждый файл, предсказание общее для дубликатов.
3. Область и сторону определять по изображению; суффикс имени файла — только подсказка.
4. Масштаба в мм нет → критерий поля ROI реализуем в относительных единицах, пока эксперты не дадут мм/px.
5. Кросс-валидация строго по исследованиям (GroupKFold), бутстрэп-ДИ; при 3–10 положительных честно писать широкие интервалы.
6. Аугментации: без поворотов (убьёт критерий оси), без горизонтальных отражений (убьёт сторону бедра) — или отражать с одновременной сменой метки стороны.
7. Спорные случаи (сколиоз, перелом, эндопротез) вынести в отдельный список и решать по ответу экспертов.
