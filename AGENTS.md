## Жёсткие правила

1. **Никаких данных организатора в git.** Не коммитить `data/`, `docs/materials/`, `docs/img/`, `docs/transcripts/`,
   `docs/TZ_full.txt`, любые `.dcm`, `.zip`, `.xlsx`, `.pdf`, `.pptx`. Пароль к материалам не писать нигде
   (ни в коде, ни в issues, ни в коммитах). Данные качаются: `LCT_PASSWORD=… scripts/download_data.sh`.
2. **Формат вывода — только официальный** (`src/dxaqc/labels.py`): `anatomical_region`, `violation_type`
   (текст через `;`, пусто при норме), `quality_prob`. Не переименовывать, не переводить.
3. **Истина в разметке — колонки критериев, не «Итог»** (`RegionLabel.truth`). Сколиоз, перелом, эндопротез —
   не нарушение.
4. **Аугментации:** без поворотов (ломает критерий оси ≤ 5°); отражение по горизонтали — только вместе со сменой
   стороны бедра; чёрные маски по краям бедра — не признак, модель не должна на них опираться.
5. **Валидация только по исследованиям** (GroupKFold по `study_dir`), метрики — с 95 % ДИ (bootstrap по исследованиям).
6. **Решение работает локально, без сети.** Никаких внешних API и облачных LLM в инференсе.
7. Не переписывать историю git, не делать force-push, не менять видимость репозитория, не удалять issues —
   это действия владельца.
8. Язык документации, issues и сообщений коммитов — русский. В конце коммита — строка `Co-Authored-By` агента.

## Как работать по очереди

- Одна задача = один issue = одна ветка `issue-<N>-кратко` = один PR в `main`. В `main` напрямую — только правки
  документации и `STATUS.md`.
- Взял задачу → метка `йода` или `claude` на issue + строка в `STATUS.md` («в работе у …»).
- Закончил или упёрся → обнови `STATUS.md` (что сделано, что проверено, что дальше), сними свою метку,
  поставь метку следующего (`claude` / `йода`) или `ждёт-владельца`, если нужно решение Андрея.
- Перед PR: `python -m pytest -q` зелёный; для кода с данными — прогон на `data/work/test`.
- Решения, которые принимает только владелец: смена архитектуры, внешние датасеты и их лицензии, всё про сдачу
  и публикацию, любые траты.
